# Aegis Receipt Standard (ARS-01)

**Status:** Draft / Request for Comments (RFC)
**Authors:** Berlin AI Labs
**Created:** April 2026

## Abstract
The Aegis Receipt Standard (ARS-01) defines a canonical JSON schema for `ToolExecutionReceipts`. This standard enables AI agents to cryptographically prove that their actions (e.g., on-chain transactions) have been inspected and approved by a Trusted Execution Environment (TEE) compliance oracle.

This ensures interoperability across different agent frameworks (ElizaOS, SendAI) and blockchains, providing a unified "receipt of compliance."

## Motivation
Currently, AI compliance firewalls act as centralized Web2 proxies. If an agent executes a transaction through an RPC, the blockchain has no mathematical proof that the transaction passed compliance rules. 

ARS-01 solves this by producing a standardized payload signed by the compliance TEE. When anchored to a blockchain (e.g., Solana SPL Memo) or used in a multisig (Squads), third-party auditors can cryptographically verify that the specific action was authorized under specific regulatory rules.

## Core Schema
The receipt MUST be a valid JSON object matching the following structure:

```json
{
  "actionId": "string",
  "toolId": "string",
  "authorizationNonce": "string",
  "parameters": {
    "wallet": "string",
    "instructionCount": "number",
    "programs": ["string"],
    "decision": "ALLOW | BLOCK | REQUIRE_HUMAN",
    "riskScore": "number"
  },
  "resultHash": "string",
  "tiemstamp": "string",
  "enclaveDid": "string",
  "compliance": {
    "eu_ai_articles": ["string"],
    "mitre_tags": ["string"]
  },
  "signature": "string"
}
```

### Fields Definitions

- `actionId`: A unique identifier generated by the agent or firewall for this specific interaction.
- `toolId`: Always `solana-transaction-firewall` or equivalent for ARS-01.
- `authorizationNonce`: A cryptographically secure random string preventing replay attacks.
- `parameters.decision`: The core outcome of the policy engine (`ALLOW`, `BLOCK`, `REQUIRE_HUMAN`).
- `resultHash`: A SHA-256 hash of the `parameters` and compliance mappings.
- `enclaveDid`: The Decentralized Identifier of the TEE that produced the signature (e.g., `did:aegis:enclave:...`).
- `compliance`: An array of standardized regulatory tags that this decision evaluated against.
- `signature`: The Ed25519 signature of the canonical JSON representation (excluding the signature field itself), signed by the `enclaveDid` private key.

## Implementation Guidelines

### Serialization for Signing
Before generating the `signature`, the JSON object (minus the `signature` field) MUST be serialized deterministically:
1. All keys sorted alphabetically.
2. No whitespace between keys, colons, or brackets.
3. Stringified using UTF-8 encoding.

### On-Chain Anchoring (Solana)
When anchored to Solana, the full ARS-01 JSON string should be provided as the payload to an SPL Memo (v2) instruction attached to the transaction it corresponds to.

```typescript
const memoIx = new TransactionInstruction({
    keys: [{ pubkey: payer, isSigner: true, isWritable: true }],
    data: Buffer.from(JSON.stringify(ars01Receipt), 'utf-8'),
    programId: new PublicKey('MemoSq4gqABAXKb96qnH8TysNcWxMyWCqXgDLGmfcHr'),
});
```

### Squads V4 Cryptographic Lock integration
When the decision is `ALLOW`, the TEE acts as a 2-of-2 co-signer on a Squads Vault. The ARS-01 receipt is stored separately (via SPL Memo or off-chain indexer), while the TEE's signature on the Squads proposal serves as the on-chain execution primitive.

## Extending ARS-01
Future versions of this standard will support zero-knowledge wrappers (zkSNARKs) to prove compliance without revealing the specific transaction parameters.
